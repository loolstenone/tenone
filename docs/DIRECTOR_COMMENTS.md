텐원 유니버스는 20개가 넘는 브랜드가 유기적으로 맞물려 돌아가는 거대한 모노레포(Monorepo) 플랫폼입니다. 저희 팀이 '보안, 체계, 안전성, 확장성'을 놓치지 않고 안정적으로 스케일업하기 위해, 앞으로 코드를 전개하실 때 상호 참고하고 논의할 수 있는 주요 목표와 아키텍처 가이드라인을 정리해 공유드립니다.

## 🎯 Current Priorities (현재 주력 과제)

### [Priority 1] Cross-Domain SSO (다중 도메인 단일 인증) 아키텍처 설계 (New)
* **제언:** 서드파티 쿠키 제한(ITP) 및 Supabase Auth 콜백 제약 환경 속에서, 서로 다른 최상위 도메인(TLD) 간 완벽한 세션 공유를 이루어내야 합니다.
* **핵심 과제:** '공유 토큰 핸드오프(Token Handoff) 메커니즘' 또는 '도메인 간 브릿지 리다이렉션(Redirection)' 전략을 깊이 있게 평가하고, 가장 견고하고 확장성 있는 구조를 채택해 주시길 당부드립니다. 이는 유니버스 생태계 연동의 가장 중요한 열쇠가 될 것입니다.

### [Priority 2] 3계층 신원 아키텍처 프론트엔드 통신 안정화
* Phase 2 통신 브릿지(`auth-context.tsx` 어댑터) 연동을 마무리하며 하위 호환성을 보장하고, 이번 멀티 도메인 SSO 설계와 자연스럽게 맞물릴 수 있도록 상태 Context의 확장성을 염두에 두시길 부탁드립니다.

### [Priority 3] 모듈화 격리 및 하이브리드 트래픽 캐싱 (중장기)
* 공용 컴포넌트와 20개 브랜드별 특화 폴더(`features/[brand]`) 간의 간섭(Side-effect) 차단 및 완전한 격리 방안 모색.
* 트래픽 분산을 위한 기능별 렌더링(SSG/ISR/SSR) 전략 수립.

## 📘 Architecture Guidelines (설계 참고/조언 사항)

### 1. 공용 코어(Common Core) 확장과 폴더 분리의 기준점
유니버스의 장기적인 안정성을 유지하기 위해 공용 인프라와 개별 브랜드 영역의 역할을 분리하는 기조를 제안합니다.
* **✅ 어댑터 확장의 영역:** 현재 진행하시는 [Priority 1] 에서는 `auth-context.tsx`를 수정하여 신규 데이터를 표준 규격으로 변환(Adapter)해 주는 통합 작업이 필수적이므로 자유롭게 전개해 주십시오.
* **✅ 브랜드별 격리의 영역:** 반면, 특정 사이트(예: 바닥, 스마컴)에만 귀속되는 특수 요구사항이 생길 경우, 공용 코드(`auth-context.tsx`, `middleware.ts` 등) 내부에 `if (brand === 'badak')` 조건문으로 분기하기보다는, 해당 브랜드의 독립된 폴더(`features/[brand]`)에서 파생 컴포넌트를 만들어 해결하는 방식을 지향합니다.

### 2. 프리뷰 환경 최적화 (포트 충돌 방지)
로컬에서 `npm run dev` 테스트 중 간헐적으로 서버가 종료되는 현상을 겪으실 수 있습니다.
* **조언:** 이는 코드 문법 오류보다는 백그라운드에 남아있는 이전 프로세스가 포트(3000번)를 점유하고 있을 확률이 매우 큽니다. 불필요한 에러 디버깅에 시간을 낭비하시기보다, 프로세스를 깔끔히 종료하시거나 `npm run dev -p 4000` 처럼 다른 대체 포트를 띄워서 쾌적한 개발 리듬을 유지하시길 권장합니다.

### 3. API 통신 규격 및 페이로드 검증(Validation) 가이드
최근 게시판 쪽에 테스트하실 때 400 Bad Request 에러(`app/api/board/posts/route.ts` 등)를 만나셨다면, 통신 프로토콜 혼동이나 필수 페이로드 누락에 기인했을 가능성이 큽니다. 원활한 API 연동을 위해 다음 명세(Specification)를 참고해 주시길 권장합니다.
* **[GET] 목록 조회 (`/api/board/posts`):** 
  - URL Query Parameter 방식을 사용합니다. (예: `?site=badak&page=1&limit=12`)
  - 여기에는 400 에러를 던지는 로직이 없으며, 파라미터가 없으면 기본값으로 안전하게 폴백(Fallback)됩니다.
* **[POST] 글 작성 (`/api/board/posts`):** 
  - ⚠️ URL 파라미터가 아닌, **HTTP Body 내 JSON 객체**로 전달해야 합니다.
  - **필수(Required):** `site`, `board`, `title`, `content` 4가지 값이 JSON 내에 반드시 포함되어야 합니다. 하나라도 누락되거나 undefined로 전송되면 Validation에 의해 400 Bad Request가 발생합니다.
  - **비회원(Guest):** `guestNickname`과 `guestPassword`가 반드시 쌍으로 전송되어야 400 에러를 피할 수 있습니다.
* **조언:** 클라이언트 연동부 작성 또는 테스트 시, GET(쿼리)과 POST(바디)의 데이터 전송 방식을 명확히 구분하시고, API 명세에 명시된 필수 상태(State) 값들이 온전히 쥐어져 있는지 점검해 주시면 디버깅이 단축될 것입니다.

### 4. RLS 보안 및 중앙 모니터링 고려
* 신규 API를 설계하실 때는 데이터 무결성과 접근 권한 보호를 위한 RLS(Row Level Security) 정책 방어를 기본값으로 고려해 주십시오.
* 나아가 전체 시스템의 장애를 파악할 수 있는 관제 시스템(Sentry 등) 확장을 위한 에러 로깅 문구도 남겨주시면 유지보수에 매우 큰 힘이 되겠습니다.
