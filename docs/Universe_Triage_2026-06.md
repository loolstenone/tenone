## 2. 근본 원인

코드 품질의 문제가 아니다 (SSOT 정착 92%, 인프라 설계 양호). **포트폴리오 전략의 문제다.**

1. **수요 검증 전에 공급을 완성** — 아이디어 1개 = 풀스택 사이트 1개. 랜딩 테스트로 충분했을 것을 마이페이지·UC·권한체계까지 구축.
2. **29개 브랜드 동시 보유 = 1인이 감당 불가능한 유지보수 표면적.**
3. **바이브 코딩으로 '만들기'가 싸짐** → 병목이 사용자 획득으로 이동했는데 시간은 계속 개발에 투입.
4. **인프라 선행 투자**(UC·capability·테넌트 격리·WIO 2-tier)는 사용자 1만 명 규모용. 지금 필요한 것은 사용자 10명.

## 4. 개발 게이트 5원칙 (모든 세션 적용)

1. **새 페이지·기능은 T1 북극성 지표에 직접 기여할 때만 만든다.** "있으면 좋은 것"은 만들지 않는다.
2. **새 브랜드 추가 전면 금지** (2026년 내). 새 아이디어는 코드가 아니라 노트에 적는다.
3. **T3 브랜드 코드 수정 금지** (빌드 수리 제외). T2는 버그 수정만.
4. **인프라 일반화 작업 동결** — UC 고도화·capability 확장·테넌트 격리 강화 등은 실사용자 100명 도달까지 보류.
5. **세션 시작 브리핑에 "이 작업이 어느 Tier·어느 지표에 기여하는가"를 명시한다.** 답할 수 없으면 작업하지 않는다.

> 핵심 문장: **"실사용자 행동이 측정되기 전에는 새 페이지를 만들지 않는다."**
> 개발 단위는 '브랜드'가 아니라 '검증할 가설'이다.
